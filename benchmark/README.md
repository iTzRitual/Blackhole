# Benchmark boundary

This directory defines the boundary between the public development benchmark and
evaluator-controlled holdout material. Gate A is approved and Gate B contract
repair is valid. The primary
development contract is one deterministic 200-event scenario with checkpoints at
50, 100, 150, and 200; the optional 400-event stress track is secondary and is
not generated here. The earlier non-scored [size calibration](calibration/README.md)
is retained as historical evidence. The public development case and visible
development expected output are present; holdout material remains absent.

## Layout

```text
benchmark/
├── README.md
├── calibration/
│   ├── README.md
│   ├── histories/
│   ├── oracle/
│   └── reports/
├── dev/
│   ├── cases/
│   ├── expected/
│   ├── contract.json                 # Gate A v1, historical
│   ├── query-bundle.json             # Gate A v1, historical
│   ├── response-contract-v2.json     # frozen public baseline boundary
│   ├── query-bundle-v2.json
│   ├── response-schema-v2.json
│   ├── generate_benchmark.py
│   └── REVIEW.md
└── holdout/
    ├── cases/
    └── expected/
```

- `dev/cases/`: the public 200-event development input.
- `dev/expected/`: visible development references for local scorer development;
  these are not holdout ground truth.
- `calibration/`: non-scored, calibration-only synthetic histories and visible calibration oracle data. It is not the final benchmark and must not be used to tune a baseline prompt.
- `holdout/cases/`: evaluator-owned holdout inputs. They are placeholders in this scaffold.
- `holdout/expected/`: evaluator-owned ground truth. It must remain unavailable to implementation agents.

## Protection policy

The holdout split is not a second development directory. In an actual benchmark run:

- the evaluator owns and provisions holdout cases and expected outputs;
- implementation agents receive neither holdout expected outputs nor derivative hints about them;
- scoring occurs in an isolated evaluator boundary;
- candidate outputs may leave the implementation environment only through the defined submission interface;
- evaluator logs and error messages must not echo protected expected content; and
- holdout data should not be committed to the implementation repository.

The tracked placeholders in this scaffold contain no cases, labels, or ground truth. A `.gitkeep` file is only a directory marker.

The calibration directory is intentionally different: its oracle is visible because
it is non-scored and exists only to calibrate length. It must remain separate from
final development and holdout material.

## Contract status

The Gate A scenario and expected values remain frozen. The historical
`contract.json`, `query-bundle.json`, and `response-schema.json` explain the
original v1 interface that invalidated the first baseline measurement. The
frozen `response-contract-v2.json` and paired `query-bundle-v2.json` define the
public semantic response boundary: subject/predicate assertions, explicit
known/inferred/unknown semantics, deterministic value normalization, duplicate
count wording, and secondary provenance scoring. The human-readable review
artifact is [benchmark/dev/REVIEW.md](dev/REVIEW.md).

The public generator is deterministic and the development evaluator is executable.
Holdout construction remains evaluator-owned and is intentionally not generated by
the implementation-facing repository.

Do not expose or derive holdout expected outputs through prompts, fixtures, trajectories, documentation, logs, or debug artifacts.
